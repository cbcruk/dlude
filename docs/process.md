# 개발 프로세스: AI 네이티브 SDLC

> 참고: [The AI-native SDLC playbook](https://claude.com/ko/resources/articles/the-ai-native-sdlc-playbook) (Anthropic).
> 이 문서는 플레이북을 1인 학습 프로젝트인 dlude에 맞게 줄인 것이다.

## 1. 원칙: 제품의 P1을 개발에도 적용한다

dlude 제품의 첫 원칙은 "진료는 사람이, 기록은 AI가. AI 출력은 무조건 초안"이다([architecture.md](architecture.md#1-원작에서-가져오는-설계-원칙)).
개발 프로세스도 같은 모양으로 둔다.

| 제품 (P1) | 개발 프로세스 |
|---|---|
| AI가 쓴 노트는 `DRAFT` | 에이전트가 쓴 intent·spec·plan·코드는 초안 |
| `:review`를 거쳐야 `:commit` | 사람이 **게이트**에서 승인해야 다음 단계로 감 |
| `assumptions[]`를 따로 표시 (P2) | 문서마다 **가정과 열린 질문** 절이 필수 |
| 실패를 성공처럼 말하지 않음 (P5) | 검증 명령 출력 없이 "완료"라고 보고하지 않음 |
| 두 모델이 엇갈리면 사람이 봄 (P4) | 리뷰 에이전트와 작성 에이전트가 엇갈리면 사람이 봄 |

**에이전트는 게이트까지 일할 수 있지만 게이트를 통과시킬 수는 없다.** 에이전트는 자기 산출물을 승인하지 않는다.

## 2. 역할

1인 프로젝트라 사람 역할은 저장소 주인 한 명이 모두 맡는다. 플레이북의 역할 이름은 "어느 모자를 쓰고 판단하는가"를 가리키는 데 쓴다.

| 플레이북 역할 | dlude에서 | 하는 일 |
|---|---|---|
| 제품 책임자 | 저장소 주인 | intent·spec 승인 |
| 기술 리드 | 저장소 주인 | plan 승인, [REVIEW.md](../REVIEW.md) 관리, 고위험 변경 판단 |
| 코드 소유자 | 저장소 주인 | PR 병합 |
| 릴리스 관리자 | 저장소 주인 | `demo` 단계 배포 승인 |
| 플랫폼 엔지니어 | 에이전트 초안 → 저장소 주인 승인 | 후크·CI·평가 구성 |
| 작성 에이전트 | Claude (구현 세션) | 각 단계 초안, 구현, 검증 |
| 리뷰 에이전트 | Claude (작성과 다른 세션) | REVIEW.md 기준 리뷰. 작성 세션의 결론을 받지 않고 diff와 문서만 받음 |

## 3. 단계와 산출물

로드맵 단계 하나([architecture.md 9절](architecture.md#9-로드맵))가 기능 하나다. 기능마다 `docs/features/<번호>-<이름>/` 폴더를 두고 아래 파일을 차례로 커밋한다. 틀은 [`docs/features/_template/`](features/_template/)에 있다.

```
intent.md ──게이트 1──▶ spec.md ──게이트 2──▶ plan.md ──게이트 3──▶ 구현(PR) ──게이트 4──▶ 병합 ──게이트 5──▶ demo 배포
```

| 단계 | 산출물 | 에이전트가 하는 일 | 게이트 (사람) |
|---|---|---|---|
| 1. 기획 | `intent.md` | 원작 글과 architecture.md를 근거로 초안. 문제·결과·영향·제약·열린 질문 | 1. "이 문제를 지금 풀 가치가 있는가" |
| 2. 설계 | `spec.md` + `docs/design/<context>.md` 갱신 | 용어 표, 리소스·커맨드, 상태 표, 오류 코드 표, 이벤트·정책, 결정(대안·대가·되돌릴 조건). semu·hemr 규약과 어긋나는 곳을 표시 | 2. "요구사항과 경계가 맞는가" |
| 3. 계획 | `plan.md` | 계획 모드에서 바꿀 파일, 작업 순서, 각 작업을 증명할 테스트. 승인 전에는 파일을 고치지 않음 | 3. "이 순서와 테스트로 spec을 증명하는가" |
| 4. 구현 | 브랜치 + PR | 실패하는 테스트 먼저 → 구현 → 검증 명령 출력을 PR 본문에 붙임 | 4. 리뷰 에이전트 결과 + 사람 판단으로 병합 |
| 5. 배포 | `demo` 단계 | `alchemy deploy --stage demo` 준비. 직접 실행하지 않음 | 5. 사람이 배포 명령 실행 |
| 6. 유지 | 새 `intent.md` 초안 | 지표 이상을 감지한 스크립트 결과로 intent 초안을 씀 (6절) | 다시 게이트 1 |

### 문서 상태

intent·spec·plan은 frontmatter에 상태를 둔다.

```yaml
status: draft        # draft | approved | superseded
approved_on:         # 사람이 채움
```

- `approved`로 바꾸는 것은 사람뿐이다. 에이전트가 승인된 문서를 고쳐야 하면 고치지 않고 새 개정 초안(`spec.r2.md`)을 쓰거나 변경 제안을 PR 본문에 적는다
- 구현 중 spec과 다르게 가야 하면 멈추고 사람에게 묻는다. 조용히 바꾸지 않는다

### 작은 변경

오타·문서 링크·의존성 패치처럼 동작이 바뀌지 않는 변경은 intent·spec·plan 없이 PR만 연다. 동작이 바뀌면 크기와 상관없이 spec부터 고친다(semu·hemr 규칙: "동작을 바꾸면 같은 PR에서 그 컨텍스트 문서를 고친다").

## 4. 구현 규칙

- **검증 명령은 하나다.** `pnpm verify` = `typecheck` + `format:check` + `test`. 에이전트는 이 출력을 붙이기 전에는 완료를 보고하지 않는다
- **버그 수정은 실패하는 테스트를 먼저 커밋한다.** 그 테스트를 통과시키려고 테스트를 고치지 않는다
- **병렬 세션은 2~3개까지.** 기능마다 git worktree 하나. 리뷰가 밀리면 세션을 늘리지 않는다
- **같은 실수가 두 번 나오면** [CLAUDE.md](../CLAUDE.md)에 한 줄 더한다. CLAUDE.md는 한 페이지를 넘기지 않는다
- **반복 작업은 서브에이전트로 만든다** (`.claude/agents/`). 후보: 리뷰 에이전트, 규칙 픽스처 작성자, OpenAPI 설명 검사기

## 5. 강제 장치

스킬과 CLAUDE.md는 권고다. 반드시 지켜야 하는 것은 후크·CI·테스트로 강제한다. 0단계(코드 뼈대)에서 `.claude/settings.json`과 `.github/workflows/`에 넣는다.

| 규칙 | 강제 장치 |
|---|---|
| 승인된 intent·spec·plan을 에이전트가 고치지 않음 | PreToolUse 후크: 대상이 `docs/features/**`이고 `status: approved`면 차단(종료 코드 2) |
| 규칙 픽스처·OpenAPI 저장본을 손으로 고치지 않음 | PreToolUse 후크: `test/fixtures/rules/**`, `docs/reference/openapi.json` 편집 차단. OpenAPI는 `pnpm openapi`로만 |
| 버그 수정 PR에서 기존 테스트를 약하게 만들지 않음 | 리뷰 에이전트 확인 항목 + 사람 판단 (자동화 어려움) |
| 편집 뒤 포맷 | PostToolUse 후크: prettier |
| 비밀 값 노출 금지 | PreToolUse 후크: `.env*`, `.alchemy/` 읽기·쓰기 차단 |
| main 직접 푸시 금지 | GitHub 브랜치 보호 |
| `demo` 배포는 사람만 | 에이전트 권한에서 `alchemy deploy --stage demo` 거부. 개인 단계(`$USER`) 배포만 허용 |
| 실제 환자 데이터 금지 | 시드·픽스처에 주민등록번호 형식 검사 테스트. 가상 데이터 표시가 없는 환자는 CLOUD 어댑터로 못 보냄(P6) |

거부 규칙만 늘리면 승인 요청이 쏟아진다. 안전한 읽기 명령(`pnpm verify`, `git status`, `git diff`)은 미리 허용한다.

## 6. 평가

평가는 두 종류다. 섞지 않는다.

| | 제품 AI 평가 | 개발 에이전트 평가 |
|---|---|---|
| 무엇을 보는가 | dlude의 요약·RAG·계정과목 추천 품질 | CLAUDE.md·스킬·후크를 바꿨을 때 에이전트가 이 저장소 작업을 여전히 잘 하는가 |
| 위치 | `apps/api/evals/` | `evals/agent/` |
| 데이터 | 가상 녹음·전사 → 기대 요약, 시험 질문 → 기대 근거. 사람 판정(`Label`)이 쌓이면 추가 | 실제로 병합된 과거 작업 20~50개 (작업 설명 + 통과해야 할 테스트) |
| 언제 돌리는가 | 프롬프트·모델·검색 설정이 바뀌는 PR | CLAUDE.md, `.claude/` 아래가 바뀌는 PR |
| 시작 | 로드맵 2단계(요약), 6단계(지식) | 병합된 작업이 10개쯤 쌓인 뒤 |

운영 중 틀린 요약이나 틀린 답이 나오면 그 사례를 회귀 평가로 더한다.

### 유지 단계: 감지는 스크립트, 대응은 단계별

P3("숫자는 코드가 계산")과 같다. 이상 감지는 모델이 아니라 `metric_snapshot`을 읽는 결정론적 스크립트가 한다. 기준은 `bands.yaml` 하나에 둔다.

| 지표 (예) | 1σ | 2σ | 3σ |
|---|---|---|---|
| 두 모델 불일치율 (P4) | 로그 | 읽기 전용 진단(어느 종류에서 엇갈리나) | intent 초안 |
| assumptions 비어 있지 않은 비율 (P2) | 로그 | 진단 | intent 초안 |
| 폴백 전환율 (P8) | 로그 | 진단 | intent 초안 |
| 미응답 호출 에스컬레이션 수 | 로그 | 진단 | intent 초안 |

3σ에서도 에이전트는 코드를 바꾸지 않는다. intent 초안을 쓰고 게이트 1로 돌려보낸다. 이 부분은 데모 배포 뒤에 만든다.

## 7. 측정

1인 프로젝트라 지표는 적게 둔다. 기능 폴더를 닫을 때 `plan.md` 끝의 **회고** 절에 적는다.

- plan과 병합된 diff가 맞았는가 (계획 밖 파일을 몇 개 고쳤나)
- 첫 PR이 리뷰 막음 없이 통과했는가, 막음은 몇 개였나
- 같은 실수의 반복 (CLAUDE.md에 더한 줄 수)
- spec 승인 뒤 요구사항을 다시 고친 횟수

## 8. 지금 상태와 남은 일

- dlude는 아직 git 저장소가 아니다. 이 프로세스는 커밋·브랜치·PR을 전제로 하므로 0단계 첫 작업이 `git init`과 GitHub 원격 저장소다
- 후크·CI·`pnpm verify`는 코드 뼈대가 생기는 0단계에서 만든다. 그전까지 5절은 사람이 지킨다
- 첫 기능 폴더는 [`docs/features/00-foundation/`](features/00-foundation/intent.md)이다
